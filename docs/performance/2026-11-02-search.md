# Launcher scoring maintenance — 2026-11-02

The ranking pass normalized the same query once per application, and full bundle-ID checks computed a complete fuzzy match even though only exact equality was used. It now prepares the query once per pass and uses a normalized equality check for the full bundle identifier. Actions-menu typeahead also prepares its query once. There is no persistent cache, no added feature, and no change to ranking bands or tie-breaking.

## Measurement

An optimized standalone Swift build scores 600 synthetic application records with names, aliases, alternate names, bundle IDs and executables, using nine query shapes for 30 rounds (162,000 records). The corpus covers literal, subsequence, absent, Unicode and invisible-format input. Three alternating runs on this Mac:

| Run | Before | After |
| --- | --- | --- |
| 1 | 2.459401 s | 2.121267 s |
| 2 | 2.414739 s | 2.165375 s |
| 3 | 2.468781 s | 2.149769 s |

Median time fell from 2.459401 to 2.149769 seconds, about 12.6%. Every run produced checksum `438954010170`. This measures scoring CPU time on a synthetic corpus; it does not measure end-to-end keypress latency, disk scans, or visual smoothness.

## Reproduce

Run from the repository root. Use the same compiler and avoid concurrent builds while measuring:

```sh
git show v1.7.34:Spotter/Core/SearchRelevance.swift > /tmp/spotter-search-baseline.swift
swiftc -O /tmp/spotter-search-baseline.swift Tools/search-benchmark.swift -o /tmp/spotter-search-before
swiftc -O -DOPTIMIZED Spotter/Core/SearchRelevance.swift Tools/search-benchmark.swift -o /tmp/spotter-search-after
/tmp/spotter-search-before
/tmp/spotter-search-after
```

The existing seeded 100,000-query scorer harness now checks prepared and string queries for identical matches and scores, including misses. Its existing relevance-band, alias, Unicode and ordering assertions remain in place. The complete release gate and an independent Debug build are required before publishing.

## Review scope

Reviewed query normalization, full bundle-ID fallback matching, ranking cache boundaries, screenshot snapshot lifecycle, crop geometry, cancellation, pointer-tap cleanup, and existing OCR changes. Existing uncommitted screenshot fixes were reviewed for inclusion, preserving their owner-requested frozen-selection and Chinese-first OCR behavior. No new product capabilities were introduced by this maintenance task. Screenshot pixel/interaction harnesses and an app build provide code-level evidence; no computer-use appearance acceptance was performed.

## Release validation

- The 56 standalone harnesses passed, including prepared-query equivalence across 100,000 seeded inputs, screenshot crop pixels and screenshot interaction checks.
- The first full gate reported `pending` for the extension helper-spawn fixture after its fixed 1.2-second wait (349 passed, 1 failed). No test or product code was changed to bypass that result. A complete second `release.sh prepare 1.7.35` run, with no concurrent app build, passed all harnesses, all 350 runtime checks and every model check. The first failure's cause was not established.
- The independent signed Debug app build passed and was atomically installed/relaunched as `/Applications/Spotter.app`, version `1.7.35-dev`.
- An offscreen bitmap containing `Hello 你好世界 Spotter 123` was correctly recognized by the real OCR implementation on a detached task. This verifies that fixture, not every font or language, and is not visual acceptance.
- Execution logs are retained in `/tmp/spotter-1.7.35-prepare.log`, `/tmp/spotter-1.7.35-prepare-retry.log`, `/tmp/spotter-1.7.35-debug-build.log`, and `/tmp/spotter-1.7.35-ocr.log`.
